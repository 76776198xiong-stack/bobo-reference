## 来源第 44—49 行

1. **目标是一套有原则和边界的自媒体商业系统，而非只卖 198 的流量漏斗。** 要知道每样东西为什么做、承担什么作用，兼顾用户、流量、IP、商业、个人信念与现实投入；每天写文案是必须的主线，网站、软件、课程等希望利用碎片时间有条不紊地推进。
2. **每件作品都应成为能力的证据。** 前端内容讲清问题，网站和软件把思想、判断、能力、创造力与审美变成可见、可用、可体验的作品。用户无需听作者自夸，也能从真实体验判断价值；做得不好会反向伤害信任。
3. **价值正循环是想建立的经营机制：** 做出真正帮助人的东西 → 用户体验、受益 → 更信任作者及其判断 → 更愿意接触、使用、传播乃至付费 → 产生反馈与资源，使作者能创造更好的作品。作者特别强调“用户觉得东西有用、这个人厉害”两种感受会交替增强。商业效果应由真实价值支撑，**不是每个触点都必须强行转化**。此链条是战略意图，不是已实证的增长模型。
4. **网站与软件在战略上可以视为同一个体系，功能上不必相同。** 网站可呈现作者对世界的认识、内容、知识、审美和互动体验；软件更偏用户日常使用及 AI，但彼此可以复用空间/方法/界面，也可以互相指向。不能将网站缩减成“目录加几篇文章”，也不能将软件缩减成“存和看”。
5. **思想不只是被讲述，更可以被体验。** 视频让用户认识作者的思考；网站让用户看到作者如何组织、展示和体验自己的世界；软件让用户把方法用于自己的生活。作品证明人，人与作品的意义又相互强化。网站的审美是体验和表达的一部分，而非事后装饰。
6. **不预先锁定网站/软件的边界，也不急于选一个壳。** 网站本身可以包含工具、交互与 AI，软件也可以承载思想、知识与审美；是否共享技术底座、多端运行，须进一步研究。评估应先看真实用户价值、经营价值和成本，不把不同维度简单加权成最高分。

3. **作者希望做到“不做营销，只做告知”。** 这是希望遵循的内容与经营姿态，作者特意指出“不能说已经给整个商业模式定了规则”。它同时约束行为的上限与下限：产品确有价值时要让适合的人知道，但不愿依靠过度宣传、说服或制造虚假期待来推进成交。对“上下限”的解释是 AI 的初步理解，待日后在具体内容里检验。
4. **按当下实际需要逐步做，不必先做完所有东西。** 作者的直觉是“当下用什么就做什么”。每天的文案是现实主线；已经有的写作工作台、空间、文件/仓库管理规则等，可以先在自己的真实工作里变成好用的作品。复用积累、解决当前摩擦，再看如何在网站展示、在软件里提供、或教给用户。**战略上理解全局，与执行时一次做一件真实需要的事，可以并存。** 后一句为 AI 提炼，不是作者确定的产品开发流程。
5. **命名仍未确定，且名称可能指不同层。** 作者现在明确：“开放世界”可以是其中一个界面，不再适合直接充当整个产品的完整称呼。作者认为“明镜”用在网页不贴切，张力不够、普通、同质化，带点古风中二感；也曾设想让“啵啵”成为主体，借鉴 Muse 的产品形态，作者认为这条路仍可考虑。网页、软件、空间、界面和 IP 形象之间的品牌/命名关系**未裁决**。不提前锁死“破茧开放世界”“明镜”或“啵啵”为总产品名。
6. **写作/文档空间的卡点可能与未确定的总产品形态有关。** 但这不必阻挡先解决作者真实的写稿问题；空间将来放在哪个界面、如何给外部用户用、是否统一代码底座，可以在看到真实使用与交互样板后再定。不要把“今天就要选总名、画出最终产品全貌”当成开发前提。

## 来源第 100—105 行

1. **一个可以在场景中动态组合的底座。** 作者用“能源召唤对应机甲，各部分从不同方向组装起来”作比喻：不是先制造一个不可改变的超级应用，而是具备一套共同能力，需要写作、对比、阅读/文档或世界管理时，组合出适配该任务的空间。比喻表达的是“共用底座、按场景组装”，并非决定一定用运行时生成代码。
2. **啵啵和空间分开。** 啵啵作为日常对话、记录、存储、提醒等更贴近人际交流的入口，参考 Muse / Grok Bot；空间负责具体任务的操作、编辑、理解与呈现。作者希望用户可以对同一个对象说不同的事情，但不需要所有任务都停留在聊天窗口。啵啵并非整个软件架构的唯一主体。
3. **产品不是 Personal Agent。** 核心是人和任意 Agent 都能使用的规则、资料与空间，用户选择模型、持有本地数据、随时更换 AI / Agent；作者不想抢存量 AI/Agent 用户，而是服务可能从未主动使用这些技术的自己的用户。
4. **IP 与产品可分别独立。** 啵啵大王作为更宽的内容账号可以直接引导用户认识啵啵 App，不必经开挂的熊。作者从设计之初希望啵啵这个 IP 和软件都能“独立于我，又代表我”；不是每个产品都必须靠作者本人出镜解释。
5. **现有资产与未匹配。** 作者认为文件管理/后台大体已经解决，本地也有相对完整的旧实现，但新理念可能和旧实现不一致；因此不能把“已能用的本地工程”和“新架构已经实现”混为一谈，需对照代码与功能验证。
6. **仍想客观打分。** 作者愿意暂时采取描述的架构，但担心维度多、其他方案可能被遗漏，想比较“是不是最好”；这应被理解为**寻求避免遗漏与降低后悔风险的决策证据**，不是请求在此刻草率宣布最优方案。

## 来源第 109—114 行

- 可暂将体系分为：**共同数据与能力底座**（格式/规则/检索/空间接口/权限）＋ **人机交互入口**（啵啵或其他 Agent）＋ **场景空间**（写作、世界、文档、对比等）；手机/电脑/网页为不同承载环境，并不自动改变数据所有权。
- “对同一个对象说话”是便利体验，“随时换 Agent”是架构独立性；二者可以并存，但前提是历史资料与语境不锁在啵啵的私有格式中，且不同 Agent 具有清晰的读写授权。最好让啵啵成为可更换的**入口**而非用户数据唯一所有者。
- 空间“组装”可能先做现成模块的选择、加载与组合，不必从第一天就让 AI 任意生成复杂 UI；美学与稳定性是信用资产，动态生成若失控可能反而损害体验。
- 关键风险不是“某个 Bot 的能力强弱”，而是旧后台能否适配**独立入口、可替换 Agent、统一资料协议、模块化空间**，以及普通用户是否真的能无感使用。
- 对方案评估不建议再做“所有功能×所有终端×所有 Agent”的巨大矩阵。先用刚性边界排除（不强制翻墙、数据自主、无需提供每人云电脑、不让更换模型导致资料消失等），再比较三个**真正不同的结构方案**：A. Bot 一体化主导；B. 空间/工具主导；C. 共用底座、啵啵入口和场景空间相互独立。评分采用“当前有证据/有原型未验证/纯设想”证据标记，重点比较低门槛、帮助用户、作品/IP 信任、替换自由、成本/维护、旧资产复用和长期扩展；没有实际测试数据时不造精确分数。最终以作者写文案这一真实场景做验证，顺带测试“同一份资料既能让 Agent 使用，又能在写作空间里直观看到和编辑”。
- 最新外部背景：Meta 2026-11 官方公开 Spaces（动态创建的应用内部定制空间），只能证明业内也在做此类交互，不证明作者方案独一无二，也不意味着必须与其竞争。参见 https://about.fb.com/news/2026/11/introducing-spaces-customize-muse-app/amp/ 。Meta Muse 官方描述其主要依赖专属云 VM，正好可作为不同架构的对照，见 https://about.fb.com/news/2026/09/introducing-muse-personal-ai-agent/ 。

## 来源第 122—127 行

1. **空间的共同逻辑：** 根据实际场景，把资料和方法转换成适合人理解、编辑、使用的界面。世界空间可把多份资料组织为一个可浏览的个人世界；文档空间可把纯文字 Markdown 转成思维导图、分块页面、自由画布等结构化呈现。写作空间与文档空间可能统一也可能不同，**未定**。
2. **空间不是独占的成品：** 这些空间是作者自己的使用经验和样板，分享给用户后，用户可随时请自己的 Agent 修改、增加、替换，按自己的问题重新组合。与固定功能清单不同，作者要交付的是可塑的使用方法和可以继续生长的工具。
3. **啵啵与 Agent、形象、模型的解耦：** 作者愿意把啵啵作为生动的默认对话入口，但不强制用户喜欢或使用啵啵。用户可以替换成 Grok Bot、Muse、DeepSeek 的其他 Bot、自己创造的形象或其他兼容 Agent；如何设计自己的角色甚至可以成为教学内容。**“换角色形象”与“更换实际 Agent/harness”技术上是两件事，需分别验证**。
4. **AI 产品的竞争策略：** 作者不以现有 AI 使用者、Agent 产品市场或模型技术领先为目标，主要争取**影响力、注意力、信任和作品价值**。用户即使不用该软件进行复杂工程开发、不长期使用啵啵也没有关系。目标用户是原本可能不会主动用 AI、但希望生活变好的人。
5. **上手门槛的设计愿望：** 作者用“只要能说话就行，不能说也能打字”描述理想的极低门槛；这是**体验目标，不是已经被验证的所有功能都可零学习使用的事实**。核心用户依然以“希望变好”这种状态/信念定义，而非 AI 熟练度。
6. **此时不必再对整体形态大规模打分。** 作者觉得架构实现方向基本明确，剩余主要是 Agent 基座、默认模型与任务成本等工程选择。AI 建议将“共同底座＋可替换入口＋空间”作为**优先架构方向**，下一步按实际场景验证，并不把具体 Harness/服务商写成不可更换的依赖。

## 来源第 141—148 行

- 产品“怎样建设出来”的真正卡点已转成**用户看到什么、何时看到、怎样与空间交互**，而非代码实现、美观或组件库选择。这个逻辑会直接决定写作工作台的界面和与整体软件的关系；作者不相信它完全能靠随做随长自然形成。
- 现在生成代码很容易，因此不必通过先写成品才知道设计有没有价值。作者提出**先研究设计逻辑，确认后再写正式代码**；写作工作台设计与整体软件设计可以同时推进、互相验证。
- 作者建议三路比较，互相借鉴而非直接拼接代码：
  1. **本地路线：** 借鉴 Muse 的“自然语言交互 + 场景空间”逻辑，从共同底座、啵啵/Agent 入口、空间组织等角度设计自己本地方案；
  2. **Claude 路线：** 趁已有 Claude 会员，让 Claude 从头、独立设计一版（既可以检验从第一性原理出发的界面，也能避免现有方案造成思维定势）；
  3. **早期方案：** 将早期文档/写作工作台在“人怎么用”上的积累当作第三套参照，避免丢弃已深入讨论过的交互逻辑。
- Work 现有历史也包括“页边”原型：它是已存在的独立写作方案，尤其可借鉴 AI 住页边、作者控制正文、意图卡和试读。但“页边”第一屏过重的部分作者曾明确不喜欢。不应将 Muse 自动生成、作者否定过的 v1 冒充第三套有价值的原型。
- **此次提出的是设计与对照方法，尚未确定最终用户界面或工程施工方案。**

## 来源第 159—163 行

**建议三版使用同一组真实用例比较：**
A. 初次用户口述一个生活问题/想法，系统怎样记录并可找回；
B. 用户打开一份 Markdown，切换阅读、结构图/画布、编辑，但始终保持一份可信资料；
C. 作者继续《高敏感》文案：找到原稿→定位结构/主线→处理暂存素材→与 Agent 协作→不丢失原话和改动→下次无缝续写。
D. 用户把默认啵啵换成其他兼容 Agent 后，原数据和空间仍可访问（这是整体产品架构验证，并非第一版写作界面必须开发的功能）。
